## The review

Most star-history tools answer one question: “how popular did this repository
become?” gitdebt keeps that fast, familiar chart, then asks the more useful
follow-up: “what did maintaining it cost?”

The result is part public analytics site, part README toolkit, and part GitHub
browser extension. Open a repo and you get its cumulative star curve beside
bug-magnet files, churn, contributors, commit heatmaps, TODO/FIXME movement,
bus factor, commit volume, language lines, and—when a package can be resolved—
downloads versus stars.

**Verdict:** the star chart makes gitdebt immediately legible; the git-history
signals make it worth keeping open. It is especially good at showing the
difference between attention and maintenance reality.

> [!IMPORTANT]
> GitHub is restricting the stargazer-timeline endpoint. Current star totals
> remain available, while new history is acquired from GH Archive. GH Archive
> records public `WatchEvent` star starts but not unstars, so archive-backed
> curves are labeled **approximate public star activity** and never presented
> as exact current membership. Repositories already cached from GitHub retain
> their exact historical snapshots.

## What feels different

- **A real star-history replacement.** Single-repo charts, multi-repo overlays,
  calendar and aligned timelines, date windows, log scale, and CSV/JSON export.
- **Repository debt from git itself.** Bug magnets, churn, contributors,
  heatmaps, TODO trend, bus factor, commit trend, and language lines.
- **Stars versus usage.** npm, crates.io, PyPI, and Docker downloads can be
  plotted against the star curve instead of treating stars as the only signal.
- **README-native output.** Static SVG charts, play-once GIF charts, repo cards,
  profile cards, badges, PNG/WebP variants, and theme-aware linkback snippets.
- **GitHub where you already work.** The anonymous MV3 extension injects the
  report into public repository pages with no account or login.
- **No account judgment.** gitdebt stores star timestamps, not stargazer
  profiles. It does not detect “fake” stars, score users, or label accounts.

## Browser extension

`extension/` is a zero-build Manifest V3 extension for Chromium and Firefox.
It activates only on public GitHub repository pages, reads the repository
context already visible there, and asks the gitdebt API for charts. It has no
login, telemetry SDK, remote code, or broad browsing-history permission.

```bash
npm --prefix extension ci
npm --prefix extension run package
```

The packaged archives are written to `extension/dist/`.

## Under the hood

| Layer | Stack | Job |
|---|---|---|
| Backend | Rust, Axum, SQLx, Postgres | ingestion queue, analysis, exports, deterministic SVG/raster rendering |
| Frontend | Astro 7, React islands, Tailwind v4 | static product pages and live client reports |
| Extension | Browser-native MV3 JavaScript | repository panel on github.com |

The backend never blocks an analysis request on GitHub pagination. Cold work
enters a durable Postgres queue. The GH Archive coordinator batches repositories
into bounded BigQuery date scans, commits a durable cursor with every window,
and keeps partial results invisible. GitHub metadata remains authoritative for
the current star total.

## Run it locally

Requirements: Rust 1.94, Node 22.13+, pnpm 11, Docker, Git, and GNU tar.

```bash
scripts/db.sh up

export GITHUB_TOKEN=ghp_...
export DATABASE_URL=postgres://gitdebt:gitdebt@localhost:5432/gitdebt
cargo run -p backend
```

In another shell:

```bash
pnpm install
PUBLIC_API_BASE=http://localhost:8787 pnpm --filter gitdebt-frontend dev
```

The API listens on `:8787`; Astro uses `:14321`. The database schema is applied
idempotently at backend startup.

## GH Archive ingestion

Production should enable the archive source in Dokploy:

```text
GH_ARCHIVE_ENABLED=1
GH_ARCHIVE_BIGQUERY_PROJECT=your-google-cloud-project
GOOGLE_APPLICATION_CREDENTIALS=/run/secrets/gitdebt-bigquery.json
GH_ARCHIVE_BIGQUERY_LOCATION=US
GH_ARCHIVE_MAX_BYTES_BILLED=25000000000
GH_ARCHIVE_BATCH_SIZE=25
GH_ARCHIVE_WINDOW_DAYS=31
GH_ARCHIVE_CONCURRENCY=1
GH_ARCHIVE_HOURLY_LAG_MINUTES=15
GH_ARCHIVE_HOURLY_MAX_HOURS=24
```

Instead of a credential file, `GH_ARCHIVE_GOOGLE_CREDENTIALS_JSON` accepts the
service-account JSON as a Dokploy secret. The identity needs permission to run
BigQuery jobs in the billing project (normally `roles/bigquery.jobUser`).
`GH_ARCHIVE_MAX_BYTES_BILLED` is a hard per-query cost guard.

Historical jobs use the public BigQuery day tables. A separate bounded follower
downloads completed hourly `.json.gz` files for forward updates. Each hour and
its matching timestamps commit atomically in Postgres; 404 means “not
published yet” and is retried without advancing the checkpoint. GH Archive
event IDs deduplicate retries and the overlap with the next BigQuery refresh.

`WORKER_COUNT=8` is safe in archive mode: it controls concurrent GitHub
metadata resolution, not BigQuery scans. `GH_ARCHIVE_CONCURRENCY` should stay
at `1` initially. `REPO_ANALYSIS_WORKERS=8` is supported, but it is a
disk/CPU-heavy setting; provision the persistent repo volume and memory for
eight simultaneous clones. `GITHUB_MAX_IN_FLIGHT_REQUESTS` defaults to `64`
and is hard-capped below GitHub's 100-concurrent-request guidance.

The Cloudflare Pages refresh workflow already consumes
`CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`; no Cloudflare secret is
used by the backend archive worker. BigQuery requires its own Google Cloud
project and credentials.
